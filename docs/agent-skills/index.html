Overview

agent-skills is a collection of skills for the Claude Code harness — each one a single SKILL.md file in its own directory at the repo root. There is no build, no test suite, no package manifest. The "code" is prompt content; edits ship by being read at invocation time.

Skills are designed to be symlinked or copied into ~/.claude/skills/<name>/SKILL.md so the harness can load them. References inside the skills (for example ~/.claude/skills/critical-review/SKILL.md from verify-work/SKILL.md) assume that install location, not the repo path.

The harness routes to a skill based on its description: frontmatter line. Treat that description as a routing prompt — it must include both what the skill does and the trigger phrases that should invoke it.

Skill file contract

Every SKILL.md must begin with YAML frontmatter:

---
name: kebab-case-slug-matching-the-directory
description: >
  One paragraph. What the skill does AND the trigger phrases that should invoke it
  ("Use when the user asks to ..."). The harness routes on this text.
---

Body conventions used across the existing skills:

  • Read-only posture is stated explicitly when true ("does not modify code, run tests, or commit"). The deliverable is named up front.
  • Numbered ## Steps with shell snippets the skill expects to run. Default-branch discovery uses git remote show origin | sed -n '/HEAD branch/s/.*: //p' rather than hardcoding main.
  • A "What this skill is NOT" or "Hard rules" section that fences off adjacent behaviours.

See Authoring a skill for the five-step recipe for adding a new skill to this collection.

Review suite architecture

The three review skills form one workflow. verify-work is an orchestrator — it spawns critical-review and test-audit in parallel as sub-agents, then synthesises their two report files into verification-summary.md.

flowchart LR U([user / parent agent]) --> V[verify-work] V -- "spawn parallel" --> CR[critical-review] V -- "spawn parallel" --> TA[test-audit] CR --> R1[(review.md)] TA --> R2[(test-review.md)] R1 --> S[verification-summary.md] R2 --> S V --> S

Renaming a severity bucket in one skill silently breaks synthesis in the orchestrator. Treat those names as a versioned API between the three skills.
